# API 명세서 작성 가이드

본 문서는 프로그램 간 요청·응답 계약을 작성하는 기준을 정의한다. 기능 명세서 및 사용자 매뉴얼과 별도로 관리한다.

> 아래 URL·ID·필드·수치·인증 방식은 작성 방법을 보여주는 가상 예시다. 실제 구현이나 검증 결과를 의미하지 않는다. 제품에 적용할 때 실제 API 계약으로 바꾼다.

## 1. 문서 목적과 대상

API 명세서는 **어떤 요청을 보내면 어떤 데이터 또는 오류가 반환되는지**를 정의한다.

| 독자 | 사용하는 목적 |
| --- | --- |
| FE 개발자 | 서버에 보낼 값과 반환 데이터의 처리 방법 확인 |
| BE 개발자 | 요청 검증·응답·오류의 구현 기준 확인 |
| QA | 정상·경계·오류 요청에 대한 기대 결과 확인 |
| 연동 개발자 | 다른 시스템에서 API를 호출하는 방법 확인 |

### 다른 문서와의 구분

| 문서 | 책임지는 내용 |
| --- | --- |
| 사용자 매뉴얼 | 사용자가 화면에서 조회하고 결과를 확인하는 방법 |
| 기능 명세서 | 입력 조건, 로딩·실패 화면, 필터 반영, 상세 이동 등 기능 동작 |
| API 명세서 | Method·URL·인증·파라미터·요청/응답·오류 코드 |
| 지표·계산식 명세서 | Availability 등 지표의 정의·산식·집계 기준 |
| 데이터 명세서 | 원천·테이블·컬럼·관계·변환·갱신 기준 |

API 명세서에서는 화면의 로딩 표현이나 지표 산식을 다시 정의하지 않는다. 관련 기능·지표 ID를 연결한다.

## 2. API 목록

API별 상세 명세 앞에 전체 목록을 작성한다. 하나의 화면이 여러 API를 사용하거나 같은 API를 여러 화면에서 사용할 수 있다. 같은 API 계약을 페이지마다 복사하지 않는다.

| API ID | 이름 | Method | URL | 관련 기능 |
| --- | --- | --- | --- | --- |
| API-PERF-001 | 설비 Availability 조회 | GET | /api/v1/performance/availability | PERF-F01 성능 조회 |

위 목록은 예시다. 실제 목록에는 제공하는 API만 기재하고 상세 명세로 연결한다.

## 3. 공통 규칙

여러 API에 동일하게 적용되는 규칙은 공통으로 한 번 정의한다. API별 명세에는 적용 여부와 차이만 작성한다.

| 항목 | 정할 내용 |
| --- | --- |
| 접속 정보 | 환경별 Base URL과 API 버전 경로 |
| 인증·권한 | 인증 정보 전달 방식, 만료·접근 제한 처리 |
| 요청·응답 형식 | JSON 등 실제 형식, 문자 인코딩·Content-Type |
| 날짜·시간 | 날짜 형식, 시간대, 구간 시작·종료 포함 여부 |
| 필드 처리 | 필수 여부, 생략·null·빈 문자열의 차이, 기본값 |
| 목록 처리 | 목록 API의 정렬·페이지 방식·기본값·최대 크기 |
| 데이터 없음 | 빈 목록·null·상태 필드 등 구분 방법 |
| 오류 | HTTP 상태, 오류 코드, 응답 구조 |

Base URL은 `/api/...` 앞에 붙는 서버 주소다. 실제 환경 주소를 확인해 작성하며, 토큰·비밀키·비밀번호는 넣지 않는다.

지원하지 않는 페이지 처리 등을 형식에 맞추기 위해 임의로 추가하지 않는다. 예를 들어 5절의 API는 단일 집계 결과를 반환하므로 페이지 처리가 없다.

## 4. API별 상세 명세 템플릿

각 API 작업은 Method와 URL을 기준으로 식별하여 작성한다.

| 항목 | 작성할 내용 |
| --- | --- |
| 기본 정보 | API ID·이름·목적·관련 기능·관련 지표 |
| Method / URL | GET·POST 등 호출 방법과 경로 |
| 인증·권한 | 필요한 인증과 호출·데이터 접근 권한 |
| 요청 파라미터 | 위치·이름·타입·필수 여부·기본값·허용값·제약 |
| 요청 예시 | 실제 형식의 경로·헤더·본문 예시. 비밀값은 자리표시자 사용 |
| 성공 응답 | HTTP 상태·필드명·타입·필수 여부·null 허용·의미 |
| 데이터 없음 | 정상적인 빈 결과를 나타내는 방식 |
| 오류 응답 | HTTP 상태·오류 코드·발생 조건·응답 예시 |
| 참조·차이 | 공통 규칙과의 차이, 관련 API·지표 명세 링크 |

### 요청값 위치의 의미

| 위치 | 의미 | 형태 예시 |
| --- | --- | --- |
| Path | URL 경로에 들어가는 값 | /equipment/{equipmentId} |
| Query | URL의 물음표 뒤에 붙는 조회 조건 | ?startDate=2026-09-01 |
| Header | 인증 등 부가 정보 | Authorization: Bearer <access_token> |
| Body | 요청 본문에 담는 값 | 등록·수정할 JSON 데이터 |

필드가 생략되거나 null인 경우를 “선택” 한 단어로만 설명하지 않는다. 실제 허용 여부와 동작을 구분한다.

## 5. 완성 예시 — 설비 Availability 조회

이 절 전체는 가상의 API 계약 예시다. 방금 조회한 값의 반올림·표시 방식은 기능 명세서에서, 계산 기준은 MET-001에서 정의한다고 가정한다.

### 5.1 기본 정보

| 항목 | 내용 |
| --- | --- |
| API ID | API-PERF-001 |
| 이름 | 설비 Availability 조회 |
| 목적 | 지정한 기간과 설비의 Availability 반환 |
| 관련 기능 | PERF-F01 성능 조회 |
| Method | GET — 데이터 조회 |
| URL | /api/v1/performance/availability |
| 인증 | Authorization 헤더의 Bearer 토큰 |
| 권한 | 성능 조회 권한 필요. 개별 설비 지정 시 해당 설비 접근 권한도 필요 |
| 지표 정의 | MET-001 참조 |
| 응답 형식 | application/json |
| 페이지 처리 | 해당 없음. 단일 집계 결과 반환 |

### 5.2 요청 파라미터

아래 항목은 모두 Query 파라미터다. 요청 Body는 사용하지 않는다.

| 파라미터 | 타입 | 필수 | 기본 동작 | 설명 | 예시 |
| --- | --- | --- | --- | --- | --- |
| startDate | 문자열 | 필수 | 기본값 없음 | 시작일, YYYY-MM-DD | 2026-09-01 |
| endDate | 문자열 | 필수 | 기본값 없음 | 종료일, YYYY-MM-DD | 2026-09-07 |
| equipmentId | 문자열 | 선택 | 생략 시 접근 가능한 전체 설비 | 조회할 설비 ID | OHT-01 |

#### 기간·입력 규칙

* KST 기준으로 시작일과 종료일을 모두 포함한다.
* 최대 30일이며 미래 날짜는 허용하지 않는다.
* 시작일은 종료일 이후일 수 없다. 존재하지 않는 날짜는 형식 오류로 처리한다.
* 예를 들어 2026-09-01~2026-09-07은 KST 09-01 00:00 이상~09-08 00:00 미만이다.
* 빈 문자열은 생략으로 취급하지 않고 오류를 반환한다.
* 전체 설비를 요청하려면 equipmentId를 생략한다. `equipmentId=` 또는 문자열 `null`을 전체 설비 의미로 사용하지 않는다.
* All 조회의 설비 합산·집계 방식은 MET-001을 따른다. 이 API 문서에서 별도 산식을 정의하지 않는다.

### 5.3 요청 예시

**설비 한 대 조회**

```http
GET /api/v1/performance/availability?startDate=2026-09-01&endDate=2026-09-07&equipmentId=OHT-01
Authorization: Bearer <access_token>
```

뜻: “9월 1일부터 7일까지 OHT-01의 Availability를 반환한다.”

**접근 가능한 전체 설비 조회**

```http
GET /api/v1/performance/availability?startDate=2026-09-01&endDate=2026-09-07
Authorization: Bearer <access_token>
```

`<access_token>`은 자리표시자다. 문서에는 실제 토큰을 넣지 않는다.

### 5.4 성공 응답

HTTP 상태: `200 OK`

```json
{
  "startDate": "2026-09-01",
  "endDate": "2026-09-07",
  "timezone": "Asia/Seoul",
  "equipmentId": "OHT-01",
  "availability": 98.26,
  "unit": "%",
  "dataStatus": "AVAILABLE"
}
```

#### 응답 필드

아래 필드는 성공 응답에 항상 포함한다. null을 허용하는 필드도 생략하지 않는다.

| 필드 | 타입 | null 허용 | 의미 |
| --- | --- | --- | --- |
| startDate | 문자열 | 아니오 | 적용한 시작일, YYYY-MM-DD |
| endDate | 문자열 | 아니오 | 적용한 종료일, YYYY-MM-DD |
| timezone | 문자열 | 아니오 | 기간 해석 기준. 이 API에서는 Asia/Seoul |
| equipmentId | 문자열 또는 null | 예 | 개별 설비 ID. 전체 조회이면 null |
| availability | 숫자 또는 null | 예 | 백분율 값. 98.26은 98.26% |
| unit | 문자열 | 아니오 | 이 API에서는 % |
| dataStatus | 문자열 | 아니오 | AVAILABLE: 값 있음 / NO_DATA: 계산할 데이터 없음 |

응답의 `availability`는 표시용 문자가 아니라 숫자다. 화면의 표시 자릿수는 기능 명세서에서 정의한다.

### 5.5 데이터 없음과 실제 0

계산할 데이터가 없는 경우도 HTTP 상태는 `200 OK`다.

```json
{
  "startDate": "2026-09-01",
  "endDate": "2026-09-07",
  "timezone": "Asia/Seoul",
  "equipmentId": "OHT-01",
  "availability": null,
  "unit": "%",
  "dataStatus": "NO_DATA"
}
```

| 상황 | availability | dataStatus | HTTP 상태 |
| --- | --- | --- | --- |
| 정상 계산값 98.26% | 98.26 | AVAILABLE | 200 |
| 실제 계산값 0% | 0 | AVAILABLE | 200 |
| 계산할 데이터 없음 | null | NO_DATA | 200 |
| 서버 처리 실패 | 성공 응답을 반환하지 않음 | 성공 응답을 반환하지 않음 | 500 |

`AVAILABLE`이면 availability는 숫자, `NO_DATA`이면 null이어야 한다. 접근 가능한 설비가 없는 전체 조회도 NO_DATA로 반환한다. 서버 처리 실패를 데이터 없음으로 바꾸지 않는다.

전체 설비 조회 응답에서는 equipmentId가 null이며, 이는 availability의 null과 다른 의미다.

### 5.6 오류 응답

오류 응답은 application/json이며 `code`와 `message` 문자열을 항상 포함한다. 프로그램의 오류 분기는 message 문구 대신 code를 기준으로 한다.

**조회 기간 초과 예시**

```http
HTTP/1.1 400 Bad Request
Content-Type: application/json
```

```json
{
  "code": "INVALID_DATE_RANGE",
  "message": "조회 기간은 최대 30일입니다."
}
```

#### 오류 코드 목록

| HTTP 상태 | 오류 코드 | 발생 조건 |
| --- | --- | --- |
| 400 | INVALID_DATE_RANGE | 기간 누락·형식 오류·역전·30일 초과·미래 날짜 |
| 400 | INVALID_PARAMETER | 빈 설비 ID 등 잘못된 파라미터 |
| 401 | UNAUTHORIZED | 인증 정보가 없거나 유효하지 않거나 만료됨 |
| 403 | FORBIDDEN | 성능 조회 또는 지정 설비 접근 권한 없음 |
| 404 | EQUIPMENT_NOT_FOUND | 지정한 설비가 존재하지 않음 |
| 500 | INTERNAL_ERROR | 서버 내부 처리 실패 |

위 코드는 예시 API의 계약이다. 실제 제품의 공통 오류 코드가 있다면 그 규칙을 참조한다. 내부 스택·쿼리·비밀정보는 오류 응답 예시에 넣지 않는다.

### 5.7 요청·응답 확인 예시

아래는 기대 결과 목록이며 실제 API 실행 결과가 아니다. 날짜 검증은 2026-09-15(KST)를 기준일로 가정한다.

| 요청 조건 | 기대 결과 |
| --- | --- |
| 09-01~09-07, 접근 가능한 OHT-01 | 200, 해당 설비 집계 결과 |
| equipmentId 생략 | 200, 접근 가능한 전체 설비 집계, equipmentId null |
| 08-17~09-15 | 양 끝 포함 30일, 기간 검증 통과 |
| 08-16~09-15 | 31일, 400 INVALID_DATE_RANGE |
| 09-10~09-01 | 기간 역전, 400 INVALID_DATE_RANGE |
| equipmentId 빈 문자열 | 400 INVALID_PARAMETER |
| 실제 값 0 | 200, availability 0, dataStatus AVAILABLE |
| 데이터 없음 | 200, availability null, dataStatus NO_DATA |
| 토큰 만료 | 401 UNAUTHORIZED |

## 6. 변경·호환성 기준

기존 호출 프로그램이 계속 동작할 수 있는지 확인하고 API 변경을 기록한다.

| 변경 | 확인할 내용 |
| --- | --- |
| 선택 응답 필드 추가 | 호출 프로그램이 알 수 없는 필드를 허용하는지 |
| 필드 삭제·이름/타입 변경 | 기존 호출에 영향이 있으므로 버전·전환 방법 결정 |
| 필수 요청값 추가 | 기존 요청이 실패하게 되는지, 이전 호출 지원 여부 |
| 허용값·오류 코드 추가 | 호출 프로그램의 분기와 예외 처리가 대응하는지 |
| null·기본값·날짜 경계 변경 | 이름이 같아도 의미가 달라지는지 |
| API 폐기 | 대체 API, 전환 방법, 사용 종료 시점 |

실제 버전 운영·폐기 일정은 프로젝트 기준을 따른다. 이 가이드에서 특정 기간이나 배포 정책을 임의로 확정하지 않는다.

## 7. 작성 확인 및 기존 양식 메모

### 작성 확인

* API 목록과 상세의 ID·Method·URL이 일치하는가?
* 요청값의 위치·타입·필수 여부·기본값·범위가 명확한가?
* 생략·빈 문자열·null의 의미가 구분되는가?
* 날짜 형식·시간대·기간 경계가 명확한가?
* 성공·데이터 없음·실패가 구분되는가?
* 응답 예시와 필드 표의 타입·필드명·null 허용이 일치하는가?
* 오류 코드마다 HTTP 상태와 발생 조건이 있는가?
* 공통 규칙·관련 기능·지표 명세 참조가 연결되는가?
* 예시 토큰은 자리표시자이며 실제 비밀값이 없는가?
* 미확정 계약과 실제 검증 결과를 구분했는가?

### 기존 양식 확인
