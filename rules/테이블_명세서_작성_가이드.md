# 테이블 명세서 작성 가이드

본 문서는 DB 테이블의 목적·컬럼·키·관계·제약조건을 일관되게 기록하는 작성 기준이다. 데이터 출처·수집·갱신·보관 정보는 필요한 경우 별도 절로 확장한다.

> 이 문서의 테이블·컬럼·타입·제약·ID·샘플 행은 가상 예시다. 실제 DB 구조나 구현·검증 결과를 의미하지 않는다. DBMS가 정해지지 않았으므로 타입 표기는 설명용이며, 실제 문서에는 해당 DBMS에서 사용하는 정확한 선언을 기록한다.

## 1. 문서 목적과 범위

테이블 명세서는 **어떤 데이터가 어디에 저장되고, 각 행과 컬럼이 무엇을 뜻하며, 어떤 제약과 관계를 갖는지** 설명한다.

주요 독자는 BE 개발자·DB 담당자·데이터 담당자·QA다.

| 문서 | 책임지는 내용 |
| --- | --- |
| 테이블 명세서 | 테이블·컬럼·타입·키·관계·NULL·기본값·제약조건 |
| 지표·계산식 명세서 | 데이터를 조합해 지표를 계산하는 정의·산식·집계 기준 |
| API 명세서 | 외부에 전달하는 요청·응답 필드와 형식 |
| 기능 명세서 | 입력·조회·저장·오류 등 기능 동작 |
| 사용자 매뉴얼 | 사용자가 화면을 조작하고 결과를 이해하는 방법 |

기본 범위는 DB 구조다. 출처·적재·변환·갱신까지 포함하면 더 넓은 데이터 명세서로 활용할 수 있다.

현재 DB를 설명하는 문서인지, 앞으로 만들 설계인지 표시한다. 미구현 설계를 실제 DB 제약으로 기록하지 않는다.

## 2. 업무 분류와 전체 목차

### 업무 분류

업무별로 테이블을 묶으면 찾기 쉽다. 같은 테이블은 한 곳에 정의하고 다른 업무에서는 참조한다.

| 업무 카테고리 예시 | 포함 데이터 예시 |
| --- | --- |
| 설비 관리 | 설비 기본 정보·운영 유효 기간 |
| 설비 운영 | 상태 이력·계획 정지 일정 |
| 알람·장애 | 알람 발생·상태 변화 |
| 이송 | 이송 요청·완료 이력 |
| 재고 | 재고 현재 상태·입출고 이력 |

### 실제 테이블 명세서 목차 예시

```text
테이블 명세서
├─ 1. 문서 개요
│  ├─ 대상 DB·DBMS·스키마
│  └─ 현재 구조 또는 설계안 구분
├─ 2. 테이블·View 목록
├─ 3. 공통 규칙
│  ├─ 이름·타입·단위
│  ├─ 시간대·기간 경계
│  └─ 키·NULL·코드값
├─ 4. 업무별 테이블 상세
│  ├─ 설비 관리
│  │  └─ equipment
│  ├─ 설비 운영
│  │  ├─ equipment_state_history
│  │  └─ planned_downtime
│  └─ 실제 제공하는 나머지 테이블
├─ 5. View 상세 — 존재하는 경우
├─ 6. 테이블 관계
├─ 7. 출처·수집·갱신·보관 — 필요한 경우
└─ 부록
   ├─ 코드 정의·관련 명세
   └─ 변경 기록·미확정 사항
```

## 3. 표기 및 공통 작성 규칙

### 3.1 이름과 타입

* 테이블·컬럼명은 실제 DB의 철자·대소문자 그대로 적고 한글 의미를 붙인다.
* 스키마가 있으면 스키마까지 식별할 수 있게 적는다.
* DBMS·버전에 따라 타입과 제약 동작이 달라질 수 있으므로 실제 환경을 기록한다.
* 문자열은 길이, 숫자는 정밀도·소수 자릿수, 날짜·시간은 시간대 저장 방식을 명시한다.
* VARCHAR(20), DECIMAL(10,2)처럼 전체 타입 선언을 적어도 된다. 길이·정밀도 열을 따로 두면 타입과 중복되지 않도록 구성한다.
* BIGINT라는 이유만으로 자동 증가라고 가정하지 않는다. 생성 방식을 별도로 적는다.

### 3.2 키와 관계 용어

| 용어 | 의미 | 예시 |
| --- | --- | --- |
| PK | 행을 고유하게 식별하는 기본키 | equipment_id |
| FK | 다른 테이블의 키를 참조하는 외래키 | 이력의 equipment_id → equipment의 equipment_id |
| UNIQUE | 중복 저장을 허용하지 않는 값 또는 컬럼 조합 | source_event_id |
| INDEX | 조회를 돕는 인덱스. 별도 UNIQUE 지정이 없으면 중복 방지 규칙이 아님 | equipment_id + start_at |
| CHECK | 값이나 컬럼 간 조건의 DB 제약 | end_at > start_at |

FK가 실제 DB에 선언돼 있는지, 업무적으로만 연결하는 논리 관계인지 구분한다.

### 3.3 NULL·기본값·코드값

* NULL 허용 여부와 NULL의 업무 의미를 함께 적는다.
* 빈 문자열·0·NULL을 같은 의미로 취급하지 않는다.
* 기본값은 실제 DB 기본값을 기록한다. 화면이나 애플리케이션이 채우는 초기값과 구분한다.
* 코드값은 가능한 값과 뜻을 표로 정의한다. 코드명만 보고 의미를 추정하지 않는다.

예: end_at이 NULL이면 “종료 시각 미확정”이라는 원천 데이터 의미를 적는다. 이를 어느 시각까지 계산에 포함하는지는 지표·계산식 명세서에서 정한다.

### 3.4 시간 기준

시간 컬럼마다 발생 시각·수집 시각·수정 시각 중 무엇인지 설명한다. 저장 시간대와 화면 표시 시간대는 구분한다.

> 예시: start_at/end_at은 UTC 시각을 저장하고, 화면 표시와 조회 기간 해석은 관련 API·기능 명세에서 KST로 변환한다. 시간 구간은 시작 포함·종료 제외다.

## 6. 완성 예시 — equipment

### 6.1 기본 정보

| 항목 | 예시 |
| --- | --- |
| 데이터 ID | DATA-003 |
| 테이블 | equipment |
| 한글명 | 설비 기본 정보 |
| 목적 | 설비 식별 정보와 운영 유효 기간 저장 |
| 한 행의 의미 | 설비 한 대의 기본 정보 |
| 상태·환경 | 가상 설계 예시. 실제 DBMS·스키마 미정 |
| PK | equipment_id |
| 관련 테이블 | equipment_state_history, planned_downtime |

### 6.2 컬럼 정의

| 순서 | 컬럼명 | 한글명·의미 | 타입·길이 예시 | NULL 허용 | 키 | DB 기본값 | 예시·비고 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 1 | equipment_id | 설비 ID | VARCHAR(20) | 아니오 | PK | 없음 | OHT-01. 등록 시 발급, 변경하지 않음 |
| 2 | equipment_name | 설비 표시명 | VARCHAR(100) | 아니오 | — | 없음 | OHT 1호기 |
| 3 | equipment_type | 설비 유형 | VARCHAR(10) | 아니오 | — | 없음 | OHT 또는 STK |
| 4 | active_from | 운영 유효 시작 시각 | TIMESTAMP | 아니오 | — | 없음 | UTC 저장 |
| 5 | active_to | 운영 유효 종료 시각 | TIMESTAMP | 예 | — | 없음 | NULL이면 종료 미확정 |

타입은 설명용이며 실제 DBMS 결정 후 시간 타입의 시간대 지원 여부까지 확정한다.

### 6.3 제약·코드

| 구분 | 예시 설계 기준 |
| --- | --- |
| PK | equipment_id 중복·NULL 불가 |
| CHECK | active_to가 있으면 active_from보다 늦어야 함 |
| 유형값 | OHT: 천장 이송 설비 / STK: 보관 설비 |
| 운영 구간 | 시작 포함·종료 제외 |
| 표시명 | 다른 설비와 이름이 같아도 이 예시에서는 허용. 식별은 equipment_id 사용 |

PK와 CHECK는 이 예시의 DB 제약 설계이며 실제 적용 확인은 별도다. 설비 유형의 허용값 적용 방식도 실제 DB에서 확인한다.

## 7. 완성 예시 — equipment_state_history

### 7.1 기본 정보

| 항목 | 예시 |
| --- | --- |
| 데이터 ID | DATA-001 |
| 테이블 | equipment_state_history |
| 한글명 | 설비 상태 이력 |
| 목적 | 설비 상태가 유지된 시간 구간을 저장 |
| 한 행의 의미 | 설비 한 대의 연속된 상태 구간 하나 |
| 상태·환경 | 가상 설계 예시. 실제 DBMS·스키마 미정 |
| PK | history_id |
| FK | equipment_id → equipment.equipment_id |
| 관련 지표 | MET-001 Availability, MET-002 Downtime |

### 7.2 컬럼 정의

| 순서 | 컬럼명 | 한글명·의미 | 타입·길이 예시 | NULL 허용 | 키 | DB 기본값 | 예시·비고 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 1 | history_id | 상태 구간 ID | BIGINT | 아니오 | PK | 없음 | 1001. 적재 애플리케이션이 고유값 발급 |
| 2 | equipment_id | 대상 설비 ID | VARCHAR(20) | 아니오 | FK | 없음 | OHT-01 |
| 3 | state | 구간 상태 코드 | VARCHAR(20) | 아니오 | — | 없음 | RUNNING |
| 4 | start_at | 상태 시작 시각 | TIMESTAMP | 아니오 | — | 없음 | UTC 저장, 시작 포함 |
| 5 | end_at | 상태 종료 시각 | TIMESTAMP | 예 | — | 없음 | UTC 저장, 종료 제외. NULL이면 미확정 |
| 6 | received_at | 마지막 수신·반영 시각 | TIMESTAMP | 아니오 | — | 없음 | 적재 애플리케이션이 UTC 시각 입력 |

received_at은 설비에서 사건이 발생한 시각이 아니다. 새 종료 시각이나 정정 내용을 반영하면 갱신한다. 기본값 없음은 컬럼을 생략해도 자동으로 현재 시각이 들어간다는 뜻이 아니다.

### 7.3 상태 코드

| 값 | 원천 데이터 의미 |
| --- | --- |
| RUNNING | 정상 가동 상태 |
| READY | 정상 대기 상태 |
| DOWN | 장애로 사용이 중단된 상태 |
| UNKNOWN | 상태를 확인할 수 없음 |

이 값을 Availability의 가용/불가로 어떻게 분류하는지는 MET-001에서 연결한다. 데이터 명세서는 상태 자체의 의미를 정의한다.

### 7.4 제약과 관계

| 항목 | 예시 기준 | 적용 위치 |
| --- | --- | --- |
| PK | history_id 고유·NULL 불가 | DB 제약 설계 |
| FK | equipment_id는 equipment에 존재해야 함 | DB 제약 설계 |
| 시간 순서 | end_at이 있으면 start_at보다 늦어야 함 | DB CHECK 설계 |
| 상태 허용값 | RUNNING, READY, DOWN, UNKNOWN만 허용 | DB CHECK 설계 |
| 같은 설비 구간 겹침 | 기대 상태는 겹침 없음. 겹치면 품질 이상으로 식별 | 적재 검증·품질 검사. 위 CHECK만으로 보장되지 않음 |
| 열린 구간 | 설비별 end_at NULL 구간 최대 1개 | 애플리케이션 검증 설계. DB 강제 방식 미정 |

**관계 설명**

```text
equipment (설비 한 대)
    1
    │ equipment_id
    N
equipment_state_history (여러 상태 구간)
```

이 예시에서는 이력이 있는 설비의 물리 삭제를 FK로 제한한다. 설비 ID는 변경하지 않는다. 실제 제품이 다른 삭제·수정 정책을 사용하면 실제 FK 동작과 함께 적는다.

### 7.5 인덱스

| 인덱스 | 컬럼 순서 | 유일성 | 목적 |
| --- | --- | --- | --- |
| PK 인덱스 | history_id | 유일 | 상태 구간 식별 |
| ix_state_equipment_start | equipment_id, start_at | 비유일 | 설비별 시작 시각 조회 지원 |

비유일 인덱스는 같은 설비의 시간 겹침이나 중복을 막지 않는다. 구간이 조회 시작 전에 시작한 경우도 조회 대상일 수 있으므로 실제 기간 겹침 조회의 성능은 쿼리·실행계획으로 별도 확인한다. 위 인덱스만으로 성능 검증 완료를 주장하지 않는다.

### 7.6 샘플 데이터

모든 시각은 UTC다. 참조 설비 OHT-01이 equipment에 존재하고 해당 구간에 운영 중이라고 가정한다.

| history_id | equipment_id | state | start_at | end_at | received_at |
| --- | --- | --- | --- | --- | --- |
| 1001 | OHT-01 | RUNNING | 2026-09-15 00:00:00 | 2026-09-15 01:00:00 | 2026-09-15 01:00:05 |
| 1002 | OHT-01 | DOWN | 2026-09-15 01:00:00 | 2026-09-15 01:15:00 | 2026-09-15 01:15:05 |
| 1003 | OHT-01 | READY | 2026-09-15 01:15:00 | NULL | 2026-09-15 01:15:05 |

**해석 예시**

* KST 09:00~10:00에는 RUNNING이다.
* KST 10:00~10:15에는 DOWN이다.
* KST 10:15부터 READY 기록이 시작됐지만 종료 시각은 아직 확정되지 않았다.
* 경계 10:00은 첫 구간에 포함되지 않고 두 번째 구간에 포함된다.
* NULL은 자동으로 “현재 시각까지 정상”이라는 뜻이 아니다. 수집 누락 여부와 계산 포함 시각은 별도 기준이 필요하다.

### 7.7 품질 사례

| 사례 | 분류·기대 처리 |
| --- | --- |
| 같은 history_id를 다시 INSERT | PK 위반. 갱신 처리인지 중복 요청인지 적재 규칙에 따라 구분 |
| 존재하지 않는 equipment_id | FK 위반 |
| end_at이 start_at보다 이전 | 시간 CHECK 위반 |
| 같은 설비에 겹치는 상태 행 | 품질 이상. PK/FK 통과만으로 정상 판단하지 않음 |
| 앞 구간 종료와 다음 시작 사이에 빈 구간 | 상태 기록 누락 가능성. 정상 상태로 임의 보정하지 않음 |
| end_at NULL 구간 여러 개 | 열린 구간 규칙 위반. 별도 검증 필요 |

위 표는 기대 규칙이며 실제 DB를 실행해 확인한 결과가 아니다.

## 8. View 작성 기준

View가 있는 경우 원천 테이블 명세를 그대로 복사하지 않고 View의 결과 구조와 생성 기준을 설명한다.

| 항목 | 작성할 내용 |
| --- | --- |
| 기본 정보 | 실제 View명·목적·한 행의 의미 |
| 결과 컬럼 | 이름·타입·NULL·계산 또는 원천 컬럼 |
| 원천·조인 | 어떤 테이블을 어떤 키로 연결하는지 |
| 필터·집계 | 제외 조건·그룹 단위·중복 처리 |
| SQL | 실제 정의 파일 또는 DB 정의 참조 |
| 갱신 | 일반 View인지, 물리화된 결과이며 별도 갱신이 필요한지 |

일반 View에 테이블과 같은 PK/FK가 물리적으로 존재한다고 가정하지 않는다. 결과의 논리적 고유 키와 실제 제약을 구분한다. 아직 View가 없으면 만들거나 명세 항목을 채우기 위해 가정하지 않는다.

## 9. 선택 확장 — 출처·갱신·품질·보관

DB 구조 외에 데이터 흐름을 설명해야 할 때 추가한다.

| 항목 | 기록할 내용 |
| --- | --- |
| 원천 | 수집 시스템·파일·API·장비 등 실제 출처 |
| 수집·갱신 | 주기·실행 계기, INSERT/UPDATE 방식 |
| 구간 종료 | 다음 상태 수신 시 이전 end_at을 어떻게 확정하는지 |
| 식별·중복 | 같은 원천 사건을 식별하는 키와 재수신 처리 |
| 지연·정정 | 늦게 도착한 데이터·과거 수정 처리 |
| 품질 검사 | 누락·중복·겹침 검사와 발견 시 처리 |
| 보관 | 보관 기간·삭제/이관 기준·담당 |
| 접근 | 읽기·쓰기 권한과 민감 데이터 포함 여부 |

**기록 예시**

> 다음 상태를 정상 순서로 수신하면 같은 설비의 이전 열린 구간 end_at을 새 상태 start_at으로 확정하고 새 구간을 저장한다. 역순 수신·동일 사건 재전송의 실제 처리 방식은 적재 명세를 참조한다. 아직 확정하지 않았다면 미확정으로 표시한다.

보관 기간·삭제·권한을 임의로 정하지 않는다. 원천 데이터와 지표 계산의 차이를 유지하고, 실제 운영 기준에 연결한다.

## 10. 작성 검토와 변경 관리

### 작성 확인

* 실제 DB 구조인지 설계안인지 명확한가?
* DBMS·버전·스키마와 실제 이름을 기록했는가?
* 테이블별 목적과 한 행의 의미가 있는가?
* 컬럼의 타입·길이·NULL·기본값·단위가 명확한가?
* PK·FK·논리 관계·인덱스·업무 검증을 구분했는가?
* 코드값과 의미, 시간대·경계가 정의돼 있는가?
* 샘플 데이터가 정의와 일치하며 참조 대상이 존재하는가?
* 구간 겹침·누락·종료 미확정을 정상으로 가정하지 않았는가?
* 관련 지표·API의 참조 컬럼과 일치하는가?
* 출처·갱신·보관이 필요한 경우 별도 기록했는가?

### 변경 영향

컬럼 삭제·이름/타입 변경, NULL 허용 변경, 키·코드값·시간 의미 변경 시 사용하는 API·지표·적재·조회 코드를 확인한다. DB 구조를 바꾸는 실행 작업과 명세 문서 정리는 구분한다.

문서 버전·개정 이력·작성/검토자 등의 관리 양식은 기존 양식을 확인한 뒤 반영한다. 현재 새 관리 양식은 확정하지 않는다.

미확정 구조나 업무 규칙은 내용·담당자·확정 필요 시점을 남긴다. 명세 작성만으로 DB 적용이나 QA가 완료됐다고 표시하지 않는다.
