# 지표·계산식 명세서 작성 가이드

이 문서는 지표의 의미·계산 기준·데이터 연결·기대 결과를 일관되게 작성하기 위한 기준이다.

> 모든 지표 정의·산식·ID·상태값·테이블·컬럼·수치는 가상의 작성 예시다. 실제 제품의 기준이나 검증 결과가 아니다. 실제 업무 정의와 데이터 구조를 확인한 뒤 적용한다. 특히 Availability·Utilization·MTTR 등은 이름만으로 계산 기준을 추정하지 않는다.

## 1. 목적과 대상 독자

지표·계산식 명세서는 **어떤 데이터를 어떤 기준으로 계산하면 어떤 의미의 값이 나오는지** 정의한다.

| 독자 | 확인할 내용 |
| --- | --- |
| 현업·기획 | 지표가 업무 의미와 일치하는지, 어떤 상황을 포함·제외하는지 |
| 개발·데이터 담당자 | 필요한 데이터, 계산 변수, 시간 경계·집계·예외 규칙 |
| QA | 입력 데이터와 기대 결과, 경계·누락·중복 처리 |
| 분석 담당자 | 지표 간 비교와 해석의 한계 |

**같은 입력과 기준을 적용하면 같은 결과가 나오도록 작성하는 것**이 목표다. 산식 한 줄만으로 완료하지 않는다.

## 2. 다른 문서와의 경계

| 문서 | 책임지는 내용 |
| --- | --- |
| 사용자 매뉴얼 | 지표의 사용자용 의미·읽는 방법·주의사항 |
| 기능 명세서 | 표시 위치·필터 적용·갱신 계기·클릭·화면 상태 |
| API 명세서 | 지표 값을 전달하는 필드·타입·요청/응답·오류 |
| 지표·계산식 명세서 | 업무 정의·산식·변수·집계·예외·계산 예시 |
| 데이터 명세서 | 원천·테이블/뷰·컬럼·키·관계·적재·변환·보관 |

계산 SQL은 구현 파일이나 별도 SQL 문서에 연결한다. SQL만 넣고 업무 정의·계산식 설명을 대신하지 않는다.

## 3. 업무 카테고리와 계산 유형

### 3.1 분류의 차이

* **업무 카테고리:** 무엇에 대한 지표인가? 목차와 탐색 기준이다.
* **계산 유형:** 어떤 방식으로 계산하는가? 작성·검증 항목을 고르는 기준이다.

| 지표 | 업무 카테고리 예시 | 계산 유형 |
| --- | --- | --- |
| Availability | 설비 운영 | 비율 |
| Utilization | 설비 운영 | 비율 |
| Downtime | 설비 운영 | 시간·기간 |
| Alarm Count | 알람·장애 | 건수·합계 |
| MTTR | 알람·장애 | 평균·분포 |
| Transfer Count | 이송 성능 | 건수·합계 |
| Lead Time | 이송 성능 | 시간·기간 |
| Transfers per Hour | 이송 성능 | 처리율·빈도 |
| Inventory Count | 재고 | 시점 값 |

실제 업무에 맞춰 카테고리를 정한다. 같은 지표가 여러 업무에서 쓰이면 대표 카테고리 한 곳에 정의하고 나머지는 참조한다.

### 3.2 계산 유형별 보충 항목

| 유형 | 반드시 정할 내용 |
| --- | --- |
| 건수·합계 | 세는 대상, 고유 키, 중복·취소·재시도 포함 여부 |
| 시간·기간 | 시작·종료 사건, 기간 경계, 미종료 구간, 중복 시간 |
| 비율 | 분자·분모, 포함·제외 대상, 분모 0, 여러 대상 합산 |
| 평균·분포 | 표본 단위, 표본 선택, 가중치, 이상값, 통계 계산 방법 |
| 처리율·빈도 | 세는 사건, 시간 분모, 단위 환산, 부분 시간 구간 |
| 시점 값 | 기준 시각, 시점 상태 복원, 최신 데이터 판단·지연 |

한 지표가 여러 특성을 가지면 함께 적용한다. 예를 들어 MTTR은 평균·분포 유형에 시간·기간 규칙도 필요하다.

### 4.1 목차 예시

```text

├─ 3. 공통 계산 기준
│  ├─ 시간대·기간 경계·단위
│  ├─ 집계·가중치·필터
│  ├─ 결측·중복·미완료 데이터
│  └─ 정밀도·반올림·데이터 지연
├─ 4. 설비 운영
│  ├─ Availability
│  ├─ Utilization
│  └─ Downtime
├─ 5. 알람·장애
│  ├─ Alarm Count
│  └─ MTTR
├─ 6. 이송 성능
│  ├─ Transfer Count
│  ├─ Lead Time
│  └─ Transfers per Hour
├─ 7. 재고
│  └─ Inventory Count
└─ 부록
   ├─ 용어·변수·상태 매핑
```

없는 지표는 추가하지 않는다. 지표마다 동일한 기본 템플릿을 적용한다.

### 4.2 지표 목록 예시

| 지표 ID | 영문명 | 한글명 | 카테고리 | 계산 유형 | 단위 | 사용 화면 |
| --- | --- | --- | --- | --- | --- | --- |
| MET-001 | Availability | 가용률 | 설비 운영 | 비율 | % | Performance Summary |
| MET-002 | Downtime | 장애 중단 시간 | 설비 운영 | 시간·기간 | 초 | Performance Summary |
| MET-003 | Alarm Count | 알람 발생 건수 | 알람·장애 | 건수·합계 | 건 | Alarm History |

ID는 문서 페이지 번호와 분리한다. 기존 ID 규칙이 있다면 따른다.

## 5. 영문 이름·계산 변수·DB 컬럼 표기

**영문 이름 + 한글 의미 + 실제 데이터 연결** 형식으로 작성한다.

```text
Availability (%) = AvailableTime / OperatingTime × 100
```

| 구분 | 표기 예시 | 의미 |
| --- | --- | --- |
| 지표명 | Availability | 업무에서 사용하는 지표 이름 |
| 계산 변수 | AvailableTime | 산식에 사용하는 개념적 값 |
| 실제 테이블 | equipment_state_history | 데이터가 저장된 테이블 |
| 실제 컬럼 | start_at | 해당 테이블의 실제 컬럼 |

* 계산 변수는 읽기 쉬운 영문으로 통일하고 한글 정의·단위를 붙인다.
* DB 이름은 실제 대소문자·철자를 그대로 쓴다. 설명을 위해 실제 이름을 바꾸지 않는다.
* AvailableTime이 DB에 존재하는 컬럼이라고 가정하지 않는다. 여러 행을 처리하여 얻는 파생 변수일 수 있다.
* 상태 코드의 영어 이름만 보고 의미를 추정하지 않는다. 실제 상태 코드와 업무 상태의 매핑을 명시한다.

## 6. 공통 계산 기준

공통으로 확정할 항목을 아래에 정리한다. 실제 값이 같은 지표만 참조하며 지표별 차이는 명시한다.

| 항목 | 반드시 정할 질문 |
| --- | --- |
| 시간대·경계 | 어느 시간대인가? 시작·종료 시각을 포함하는가? |
| 시간 단위 | 원시 시간과 계산·표시 단위는 무엇인가? |
| 계산 대상 단위 | 한 기록·설비·설비군·일자 중 무엇에 대한 값인가? |
| 대상 선택 | 기간 중 운영 시작·종료한 설비를 어떻게 포함하는가? |
| 사건 시각 | 발생 시각과 수집 시각 중 어느 것을 기준으로 하는가? |
| 여러 대상 합산 | 단순 평균, 가중 평균, 분자/분모 합산 중 무엇인가? |
| 필터 | 계산 대상 변경인지, 표시 집계 단위만 변경하는지? |
| 중복 | 무엇을 동일 기록으로 보고 어떻게 한 번만 처리하는가? |
| 결측·상태 충돌 | 없거나 상충하는 데이터를 정상·0으로 간주하는가? |
| 미완료 | 종료 시각 없는 작업·장애를 포함할 것인가? |
| 지연 데이터 | 어디까지 수집한 데이터인지, 뒤늦은 기록으로 과거 값이 바뀌는가? |
| 정밀도·반올림 | 중간 계산 정밀도와 최종 반올림 방식은 무엇인가? |
| 계산 불가 | 결과 없음과 오류를 어떻게 구분하는가? |

**공통 기준 문장 예시**

> 모든 예시 시간 구간은 KST 기준이며 시작 포함·종료 제외로 처리한다. 계산 중 시간은 초 단위를 유지하고 중간 반올림을 하지 않는다. 계산 결과와 데이터 없음은 구분하며, 화면 표기와 API 표현은 각각의 명세에 연결한다.

기간이 길어졌다고 반올림한 일별 비율을 단순 평균하지 않는다. 원시 분자·분모 또는 정의된 가중치로 다시 집계한다.

## 8. 데이터 출처·변수 연결·SQL 참조

### 8.1 원천 연결표 예시

아래 DB 식별자는 모두 가상이다. 실제 문서에서는 데이터 명세서와 일치시킨다.

| 데이터 명세 | Table / View | 사용 컬럼 | 한 행의 의미 |
| --- | --- | --- | --- |
| DATA-001 | equipment_state_history | equipment_id, state, start_at, end_at | 설비 한 대의 상태 유지 구간 |
| DATA-002 | planned_downtime | equipment_id, start_at, end_at | 설비 한 대의 계획 정지 구간 |
| DATA-003 | equipment | equipment_id, active_from, active_to | 설비와 운영 유효 기간 |

### 8.2 계산 변수 연결표 예시

| 변수 | 연결 데이터 | 계산 방법 |
| --- | --- | --- |
| ObservationTime | 조회 기간, DATA-003 | 조회 기간과 설비 운영 유효 기간의 겹치는 길이 |
| PlannedTime | DATA-002 | 관측 구간 안의 계획 정지 구간을 합쳐 길이 계산 |
| OperatingTime | ObservationTime, PlannedTime | ObservationTime − PlannedTime |
| Downtime | DATA-001 | 운영 대상 구간 내 사용 불가 상태의 합집합 길이 |
| AvailableTime | OperatingTime, Downtime | OperatingTime − Downtime |

계획 정지 여러 행과 상태 이력 여러 행을 단순 조인하면 행이 늘어나 시간이 중복 합산될 수 있다. 각 구간의 의미·중복 제거·설비 키로의 연결 방법을 명시한다. 특정 SQL 작성법을 강제하는 대신 기대 계산을 정의한다.

### 8.3 상태 매핑 예시

| DB state 값(가상) | 업무 상태 | Availability 처리 |
| --- | --- | --- |
| RUNNING | 정상 가동 | 가용 |
| READY | 정상 대기 | 가용 |
| DOWN | 장애 중단 | 사용 불가 |
| UNKNOWN | 상태 확인 불가 | 품질 문제, 계산 불가 |

UNKNOWN이나 누락을 READY로 간주하지 않는다. 실제 매핑은 업무 담당자와 데이터 명세에서 확인한다.

### 8.4 구현 SQL 연결

SQL·View·함수·코드가 있으면 실제 경로/이름과 적용 버전 또는 변경 식별자를 기록한다. 아직 구현하지 않았다면 `구현 연결: 미확정`으로 표시한다. 이 문서의 가상 테이블명을 실제 구현으로 표시하지 않는다.

## 9. 완성 예시 — Availability

### 9.1 기본 정의

| 항목 | 예시 정의 |
| --- | --- |
| ID·이름 | MET-001 / Availability / 가용률 |
| 카테고리·유형 | 설비 운영 / 비율 |
| 업무 의미 | 운영 대상 시간 중 설비가 사용 가능한 상태였던 시간의 비율 |
| 가용 상태 | RUNNING 또는 READY |
| 사용 불가 상태 | DOWN |
| 단위 | % |
| 해석 | 값이 높을수록 운영 대상 시간 중 사용 가능한 시간이 많음. 실제 작업 수행 비율과 같지 않음 |
| 원천 | 8.1~8.3의 가상 데이터와 상태 매핑 |

### 9.2 계산식과 단위

```text
OperatingTime = ObservationTime − PlannedTime
AvailableTime = OperatingTime − Downtime
Availability (%) = AvailableTime / OperatingTime × 100
```

모든 시간 변수의 계산 단위는 초다. 아래 설명 표에서는 읽기 편하도록 시간·분으로도 표현한다.

| 변수 | 정의 |
| --- | --- |
| ObservationTime | 조회 구간과 설비의 운영 유효 기간이 겹치는 총 시간 |
| PlannedTime | ObservationTime 안의 계획 정지 구간을 합친 시간 |
| OperatingTime | 계획 정지를 제외한 계산 대상 시간 |
| Downtime | OperatingTime 안의 DOWN 구간을 합친 시간 |
| AvailableTime | OperatingTime 중 DOWN이 아닌, 정상 상태로 확인된 시간 |

누락·UNKNOWN·서로 다른 상태의 충돌이 있으면 단순 차감 산식으로 정상 값을 만들어내지 않고 아래 품질 기준을 적용한다.

### 9.3 대상·시간·집계 기준

| 항목 | 예시 기준 |
| --- | --- |
| 시간 경계 | KST, 시작 포함·종료 제외 |
| 날짜 필터 | 09-01~09-07 선택이면 09-01 00:00 이상~09-08 00:00 미만 |
| 설비 | 선택한 설비 중 조회 구간에 운영 유효 기간이 있는 설비 |
| 계획 정지 | 운영 유효 구간 안의 계획 정지 시간을 제외 |
| 장애 겹침 | 같은 설비의 DOWN 구간은 합쳐서 계산 |
| 계획 정지와 장애 겹침 | 계획 정지에 포함된 장애 시간은 Downtime에서 제외 |
| 설비 여러 대 | ΣAvailableTime / ΣOperatingTime × 100 |
| 여러 날짜 | 반올림한 일별 % 평균이 아니라 시간 합계로 다시 계산 |

### 9.4 결측·예외·데이터 확정 기준

| 상황 | 예시 처리 |
| --- | --- |
| OperatingTime = 0 | 계산 불가, 비율 값 없음 |
| 운영 대상 구간의 상태 기록 누락 | 계산 불가. 누락을 정상으로 간주하지 않음 |
| UNKNOWN 또는 상충 상태 | 계산 불가, 품질 확인 필요 |
| 동일한 DOWN 구간 중복 | 시간 합집합으로 한 번만 계산 |
| end_at 없음 | 데이터가 연속 수집됐음이 확인된 시각까지만 잠정 구간으로 처리 |
| 요청 종료보다 데이터 확인 시각이 이름 | 전체 요청 구간의 확정값을 만들지 않고 계산 불가 처리 |
| 종료 < 시작 등 잘못된 기록 | 품질 오류로 계산 불가 |
| 대상 설비 없음 | 계산 불가 |
| 일부 설비만 계산 불가 | 해당 설비를 조용히 빼지 않고 전체 집계도 계산 불가 |

이 예시는 전체 구간이 확인된 경우만 값을 제공하는 정책이다. 실제 제품이 부분 집계·잠정값을 제공한다면 데이터 포함 범위와 잠정 여부를 별도로 정의해야 한다.

뒤늦은 기록 정정이 있으면 영향받는 과거 기간을 재계산하며 과거 값이 달라질 수 있다. 데이터 출처의 확인 시각과 계산 기준 버전은 추적 가능해야 한다. 실행·노출 방식은 구현 및 API/기능 명세에서 연결한다.

### 9.5 정상 계산 예시

관측 구간은 08:00~18:00, 설비 OHT-01은 전체 구간 동안 운영 대상이다. 이외 상태는 RUNNING 또는 READY로 빈틈없이 확인됐다고 가정한다.

| 입력 | 구간 | 길이 |
| --- | --- | --- |
| ObservationTime | 08:00~18:00 | 10시간 |
| 계획 정지 | 12:00~14:00 | 2시간 |
| 장애 | 15:00~16:00 | 1시간 |

```text
OperatingTime = 10 − 2 = 8시간
AvailableTime = 8 − 1 = 7시간
Availability = 7 / 8 × 100 = 87.5%
```

### 9.6 중복·계획 정지 겹침 예시

다음은 동일한 08:00~18:00 관측 구간의 별도 사례다.

| 입력 | 구간 |
| --- | --- |
| 계획 정지 | 12:00~14:00 |
| DOWN 기록 A | 11:30~12:30 |
| DOWN 기록 B | 12:00~13:00 |
| DOWN 기록 C | 15:00~15:30 |

1. A와 B를 합치면 11:30~13:00이다.
2. 계획 정지와 겹치는 12:00~13:00을 제외하면 11:30~12:00, 30분이다.
3. C 30분을 더하면 Downtime은 총 60분이다.
4. OperatingTime 8시간, AvailableTime 7시간으로 Availability는 87.5%다.

A·B·C의 원래 길이를 단순 합산해 2.5시간을 빼면 잘못된 값이 된다.

### 9.7 설비 여러 대 집계 예시

| 설비 | OperatingTime | AvailableTime | 개별 Availability |
| --- | --- | --- | --- |
| A | 8시간 | 7시간 | 87.5% |
| B | 2시간 | 1시간 | 50.0% |
| 합계 | 10시간 | 8시간 | 80.0% |

```text
전체 Availability = (7 + 1) / (8 + 2) × 100 = 80.0%
```

개별 비율의 단순 평균 68.75%는 이 지표의 전체 집계값으로 사용하지 않는다.

### 9.8 결과와 연결 문서

| 항목 | 연결 기준 |
| --- | --- |
| 원시 계산 | 중간 반올림 없이 계산 |
| 화면 표시 예시 | 소수점 첫째 자리, 반올림. 화면 표기는 기능 명세서 참조 |
| API 연결 예시 | API-PERF-001, availability는 백분율 숫자 |
| 계산 불가의 API 표현 | availability null, dataStatus NO_DATA. 실제 계약은 API 명세서 참조 |
| 품질 사유 | 계산 불가 사유는 구분해 기록. 현재 예시 API는 상세 사유 필드를 정의하지 않음 |
| 화면 | Performance Summary, 지표 ID MET-001 참조 |
| SQL 구현 | 미확정. 가상 테이블로 실제 구현 완료를 주장하지 않음 |

서버 장애로 계산 요청이 실패한 경우는 정상적인 계산 불가 결과로 바꾸지 않고 API 오류로 구분한다.

## 10. 계산 유형별 추가 예시

모든 사례는 가정이며 실제 제품에 동일 산식을 적용하라는 의미가 아니다.

### 10.1 건수·합계 — Alarm Count

**정의 예시:** 조회 구간에 발생한 고유 알람 사건 수. 전송 재시도와 동일 알람의 상태 갱신은 다시 세지 않는다.

```text
AlarmCount = CountDistinct(AlarmEventId)
```

| 행 | 사건 ID | 기록 내용 | 건수 반영 |
| --- | --- | --- | --- |
| 1 | E001 | 최초 발생 | 1 |
| 2 | E001 | 전송 재시도 | 0 |
| 3 | E001 | 해제 상태 갱신 | 0 |
| 4 | E002 | 별도 알람 발생 | 1 |

기대 결과는 2건이다. 설비 번호만으로 중복 제거하지 않고 실제 사건 고유 키를 사용한다. 발생 시각이 조회 구간 밖인 알람의 해제 기록만 들어왔다면 발생 건수에 포함하지 않는다.

### 10.2 시간·기간 — Lead Time

**정의 예시:** 완료된 작업의 요청부터 완료까지 걸린 실제 경과 시간. 취소·미완료 작업은 제외한다.

```text
LeadTime = CompletedAt − RequestedAt
```

| 값 | 예시 |
| --- | --- |
| RequestedAt | 09:58 |
| CompletedAt | 10:07 |
| LeadTime | 9분 |

조회 구간이 10:00~11:00이고 **완료 시각 기준으로 표본을 선택**한다면 이 작업은 포함하며 전체 9분을 사용한다. 구간 안의 7분으로 잘라내지 않는다.

기간 내 설비 중단 시간을 구하는 Downtime은 구간을 잘라 계산할 수 있지만, 완료 작업의 전체 소요 시간인 Lead Time과는 목적이 다르다. 시간 유형이라고 모든 지표에 같은 자르기 규칙을 적용하지 않는다.

### 10.3 평균·분포 — MTTR와 P95

**MTTR 정의 예시:** 조회 구간 안에 복구 완료된 장애의 전체 복구 소요 시간 평균. 미복구 건은 이 평균에서 제외하고 별도 미복구 건수로 구분한다.

```text
MTTR = Sum(RepairDuration) / RecoveredIncidentCount
```

복구 시간 10분·20분·60분이면 `90 / 3 = 30분`이다. 건수가 0이면 계산 불가이며 0분으로 표시하지 않는다. 현업이 복구 시간의 시작점을 장애 발생·인지·수리 시작 중 어디로 정하는지 반드시 확정한다.

**P95 계산 방법 예시:** 최근접 순위법(nearest-rank)을 사용한다고 명시한다. 정렬된 표본 n개 중 `ceil(0.95 × n)`번째 값을 선택한다.

표본 10개가 1, 2, …, 10분이면 순위는 `ceil(9.5) = 10`, P95는 10분이다. 보간 방식과 결과가 다를 수 있으므로 DB 함수 이름만 적지 않고 계산 방법과 기대값을 남긴다. 이 예시는 소표본에도 값을 제공하며 표본 수를 함께 관리한다고 가정한다.

### 10.4 처리율·빈도 — Transfers per Hour

**정의 예시:** 관측 시간 안에 완료된 고유 이송 작업 수를 실제 관측 시간으로 나눈다.

```text
TransfersPerHour = CompletedTransferCount / (ObservationSeconds / 3600)
```

90분 동안 완료한 이송 120건이면 `120 / 1.5 = 80건/시간`이다. 90분을 1시간이나 2시간으로 반올림하지 않는다. 취소는 제외하고 재시도 중복은 작업 고유 키 기준으로 한 번만 계산한다고 가정한다.

### 10.5 시점 값 — Inventory Count

**정의 예시:** 지정한 시각 직전까지 반영된 입출고 결과의 재고 수. 하루의 입고 합계와 다르다.

```text
InventoryAtT = OpeningInventory + InboundBeforeT − OutboundBeforeT
```

초기 재고 100개, T 이전 입고 20개, 출고 5개면 재고는 115개다. 이 예시는 시점 T와 같은 시각의 사건을 제외한다. 같은 시각 사건을 포함하는 시스템이면 그 기준을 명시한다.

스냅샷 데이터로 계산하는 실제 제품이라면 “T 이전 최신 스냅샷”과 그 이후 증감 반영 여부·데이터 지연을 정의한다. 재고 스냅샷들을 시간별로 합산하지 않는다.

## 11. 필터·사용 화면·중복 관리

### 11.1 필터 영향 예시

| 필터 | 지표 계산 영향 | 명세 위치 |
| --- | --- | --- |
| 기간 | 관측 구간과 포함 사건 변경 | 지표의 시간 기준 + 기능의 적용 시점 |
| 설비 | 포함할 설비 집합 변경 | 지표 대상 선택 + 기능의 필터 적용 |
| 시간별/일별 | 구간별로 동일 규칙 재집계 | 지표 집계 기준 |
| 목록 검색어 | KPI에 적용하지 않는 경우 계산 영향 없음 | 기능 명세서 |

필터 조합마다 지표 정의를 복사하지 않는다. 계산 방식이 달라지는 예외만 명시한다.

### 11.2 여러 화면에서 같은 지표 사용

| 화면 | 지표 | 정의 참조 | 화면별 차이 |
| --- | --- | --- | --- |
| Performance Summary | Availability | MET-001 | 기간 전체 KPI |
| Equipment Detail | Availability | MET-001 | 선택 설비, 시간별 추이 |

동일 지표라면 한 곳에 정의한다. 계획 정지를 포함하는 Availability와 제외하는 Availability처럼 업무 의미 자체가 다르면 별도 지표 또는 명시적인 계산 기준 버전으로 구분한다. 이름이 같다는 이유로 다른 계산을 숨기지 않는다.

## 12. 계산 검증과 변경 영향

### 12.1 검증 데이터 구성

입력 행·시간 구간·대상 조건·기대값을 함께 남긴다. 숫자 결과만 기록하면 계산 차이의 원인을 찾기 어렵다.

| 검증 ID | 대상 | 입력·조건 | 기대 결과 |
| --- | --- | --- | --- |
| MET-001-T01 | 정상 | 관측 10h, 계획 정지 2h, 대상 구간 장애 1h | 87.5% |
| MET-001-T02 | 중복 | 9.6의 겹치는 DOWN 구간 | 중복 차감 없이 87.5% |
| MET-001-T03 | 여러 설비 | A 7/8h, B 1/2h | 전체 80.0% |
| MET-001-T04 | 분모 0 | 전 구간 계획 정지 | 계산 불가 |
| MET-001-T05 | 실제 0 | 운영 대상 전 구간 DOWN | 0.0% |
| MET-001-T06 | 상태 누락 | 운영 대상 중 10분 미확인 | 계산 불가 |
| MET-001-T07 | 기간 경계 | 종료 시각에 시작한 장애 | 이번 구간 장애 시간에 미포함 |
| MET-003-T01 | 사건 중복 | E001 세 행, E002 한 행 | 2건 |

이 표는 기대 결과이며 실제 실행·통과 기록이 아니다. 실행 환경과 결과는 QA 기록 또는 구현 테스트에서 연결한다.

### 12.2 기준 변경

다음 변경은 과거 값과 비교에 영향을 줄 수 있으므로 관련 화면·API·데이터·검증 예시를 함께 확인한다.

* 상태의 가용/불가 분류 변경
* 계획 정지 포함·제외 변경
* 표본 선택 시각 또는 시간대 변경
* 단순 평균에서 가중 집계로 변경
* 결측·중복·지연 처리 변경
* 백분위 계산 방법 변경

기준이 바뀌면 적용 시점, 과거 데이터 재계산 여부, 이전 기준과의 비교 가능 여부를 기록한다. 기존 양식이 있으면 변경 기록에 활용한다.

## 13. 작성 확인 및 보류 메모

### 작성 확인

* 업무 카테고리와 계산 유형이 구분되는가?
* 영문명·한글 의미·단위가 있고 변수와 실제 컬럼이 구분되는가?
* 이름만으로 계산 기준을 추정하지 않았는가?
* 분자·분모·표본·기간 경계·상태 분류가 명확한가?
* 필터와 여러 설비·기간 집계 기준이 있는가?
* 누락·중복·겹침·미완료·분모 0을 구분하는가?
* 데이터 테이블·컬럼뿐 아니라 변수 산출 방법과 연결 관계가 있는가?

* 계산 예시를 따라가면 같은 기대값에 도달하는가?
* 실제 품질 오류와 정상적인 데이터 없음을 숨기지 않는가?
* 같은 지표를 페이지별로 중복 정의하지 않았는가?
* 기준 변경 시 과거 값과 사용처의 영향을 확인하는가?

### 보류 메모

문서 버전·개정 이력·작성/검토자 등 관리 양식은 기존 양식을 확인한 뒤 반영한다. 현재 가이드에서 새 양식을 확정하지 않는다.

실제 지표에서 아직 정하지 않은 기준은 `미확정: 내용 / 결정 담당 / 확정 필요 시점`으로 남긴다. 이 문서의 예시는 현업의 계산 기준 승인이나 실제 데이터 검증을 대신하지 않는다.
