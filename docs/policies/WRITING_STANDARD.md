# 공통 Markdown 작성 표준

## 1. 적용 범위와 원본

모든 회사·제품의 조사, 문서 작성, 검토 보고에 같은 분류 규칙을 적용한다. 업무 내용을 담는 정본은 Markdown이다. JSON은 설정·상태·증거 인덱스·변환 중간 표현에 사용하고 문서 내용을 별도 정본으로 이중 관리하지 않는다. 문서 유형별 상세 항목은 `rules/`를 따른다.

폰트·제목 크기·페이지 여백·머릿글·바닥글·마지막 페이지·표 스타일·배경·강조 마커는 회사 테마에서 관리한다. Markdown에는 의미와 구조를 기록한다. 제품별 사실을 테마에 넣거나 회사별 디자인을 제품 내용에 직접 삽입하지 않는다.

## 2. 분류와 고정 인터페이스

```text
workspaces/{company_id}/{product_id}/{run_id}/
├─ scope/
│  └─ scope-001.md
├─ research/
│  ├─ inventory/
│  │  ├─ index.md
│  │  └─ sources.md
│  ├─ architecture/
│  │  ├─ overview.md
│  │  └─ data-flow.md
│  ├─ behavior/pages/{page_id}.md
│  ├─ data/
│  │  ├─ apis/{api_id}.md
│  │  ├─ metrics/{metric_id}.md
│  │  └─ tables/{table_id}.md
│  └─ reconcile/
│     ├─ conflicts.md
│     └─ findings.md
├─ sources/evidence-index.json
├─ evidence/
│  ├─ captures/
│  └─ queries/
├─ outlines/{outline_id}.md
├─ documents/{type}/
│  ├─ index.md
│  └─ sections/{stable_id}.md
├─ reviews/
│  ├─ facts/{review_id}.md
│  ├─ independent/{review_id}.md
│  └─ style/{review_id}.md
└─ delivery/{delivery_id}.md
```

- 회사·제품·실행 ID는 설정으로 받고 다른 실행 자료를 묵시적으로 섞지 않는다.
- `type`과 파일 목록은 문서 유형·workflow 설정에서 선언한다. 표시 제목 변경을 파일명 변경으로 연결하지 않는다.
- 페이지·API·지표·테이블·절은 안정적인 ID를 쓴다. 파일 ID와 경로는 제품의 명시적 workflow plan에 선언한 kebab-case를 사용하고 상대 경로 이동 요소나 절대 경로를 받지 않는다.
- 하나의 거대한 조사 파일에 전부 쓴 뒤 나누지 않는다. 첫 조사부터 위 분류 파일에 저장한다.
- `INDEX.md`는 범위, 순서 있는 절 링크, 공통 참조, 미확정 요약을 제공한다. 절 순서는 파일명 정렬이 아니라 index와 설정으로 결정한다.
- 공통 정의는 한 번 작성한다. 다른 페이지는 적용 여부와 차이를 적고 정의 파일/ID로 연결한다.
- 각 파일에는 단일 작성 소유자가 있다. 소유권과 reviewer는 `scope/scope-001.md` 및 실행 설정에서 관리한다.

분류 prefix와 필수 제목은 `policies/artifacts.json`, 실제 파일 목록은 제품 workflow plan이 원본이다. 위의 index·overview 등의 이름은 해당 prefix 안에서 plan에 선언할 수 있는 예시이며 엔진이 자동 생성하는 기본 파일명이라는 뜻은 아니다. `kind`는 stage ID와 구분하며 화면은 `page`, API는 `api`, 지표는 `metric`, 테이블은 `table`을 쓴다.

## 3. 읽는 문서와 관리 데이터 분리

Markdown에는 제목, 설명, 표, 예시와 사람이 이해할 수 있는 링크만 쓴다. 내부 근거 번호, 해시, 담당 에이전트 ID, JSON 주석, 관리용 절 번호와 로컬 절대 경로는 본문에 쓰지 않는다.

동일 경로의 관리 정보는 작업 루트의 `.metadata/`에 JSON으로 보관한다. 예를 들어 `research/behavior/pages/summary.md`의 관리 파일은 `.metadata/research/behavior/pages/summary.md.json`이다. ID·출처 연결·담당자·상태는 도구가 이 파일에서 검사한다. 근거 번호를 사람이 복사해 본문에 넣지 않는다.

- 폴더마다 `INDEX.md`를 두고 문서 제목과 상대 링크로 위치를 안내한다.
- 미확정 내용은 본문에서 “확인 필요: 최소 지원 브라우저 버전”처럼 읽기 쉽게 표시한다.
- 출처가 독자에게 필요하면 “운영 정책”, “조회 API 설명”처럼 이름으로 설명한다.
- 공개 참고자료는 문서 설정의 `public_references`에 사람이 읽는 제목과 공개 URL을 지정한 경우만 출력한다.
- 관리 상태는 pending / confirmed / not_applicable이다. 검토 판정은 pass / changes_requested다. 상태값 자체를 최종 문서에 나열하지 않는다.
- confirmed는 근거를 갖춘 작성 상태이며 독립 검토 완료와 다르다.

## 4. 독자별 문체

| 문서 | 독자·문체 | 피할 표현 |
| --- | --- | --- |
| 사용자 매뉴얼 | 사용자가 할 일을 순서대로 설명한다. “기간을 선택한 후 Search를 누르세요.” | 내부 클래스·SQL·모호한 “적절히 처리” |
| 기능 명세서 | 조건→행동→기대 결과를 단정 가능한 기준으로 쓴다. “기간 초과 시 조회하지 않고 안내를 표시한다.” | “정상 동작한다”, “필요시 처리” |
| API 명세서 | 실제 필드명·타입·허용값·누락/null 의미를 정확히 쓴다. | 가상 필드와 실제 계약 혼합 |
| 지표·계산식 명세서 | 영문 지표·변수와 한글 업무 정의를 연결한다. | 이름만 보고 추정한 산식 |
| 테이블 명세서 | 실제 Table/View·Column 이름, 한 행의 단위, 키·제약을 명시한다. | 계산 변수와 DB 컬럼 혼동 |
| 조사·검토 보고 | 확인한 사실, 근거, 제한, 다음 조치를 간결하게 쓴다. | 구현자 주장 인용만으로 통과 판정 |

시니어 문서팀의 말투는 차분하고 직접적이다. 칭찬·홍보·과장·불필요한 사과를 넣지 않는다. 한 문장에 한 기준을 적고 주어와 적용 범위를 명확히 한다. 모르는 내용을 전문 용어로 가리지 않는다. “항상”, “모두”, “실시간”, “보장”은 해당 범위 전체의 증거가 있을 때만 사용한다.

## 5. 사실·기대·관찰 분리

기능 명세의 기대 동작과 현재 실행의 관찰 결과는 다를 수 있다. 승인 문서와 코드가 다르면 어느 하나를 조용히 덮어쓰지 말고 충돌로 등록한다.

| 구분 | 내용 | 확인 자료 | 상태·제한 |
| --- | --- | --- | --- |
| 기대 | 조회 기간은 최대 30일이다. | 승인된 기능 명세서의 조회 기간 기준 | 가상 예시 |
| 관찰 | 지정 테스트 환경에서 31일 조회 요청이 성공했다. | 기간 조회 화면과 실제 API 응답 | 해당 계정·환경에서 확인한 가상 예시 |
| 판단 | 기대와 관찰이 다르다. | 위 기준과 실행 결과 비교 | 제품 결함 여부는 담당자가 판정하는 가상 예시 |

위 내용은 가상 예시다. 본문에는 자료명과 읽을 수 있는 링크를 쓰고, 내부 증거 ID 연결은 `.metadata/`의 사이드카와 `sources/evidence-index.json`에서 관리한다. 관리 데이터에는 경로·리비전·수집 시각·환경·계정 역할·조회 조건·잘림 여부·해시를 남기고 비밀번호나 토큰을 넣지 않는다. 링크만 존재하고 실제 내용이 주장을 뒷받침하지 않으면 검증 통과가 아니다.

### 미확정 기록 예시

```markdown
> [!WARNING] 확인 필요: Availability의 계획 정지 제외 기준을 확인하지 못했다.
> 담당: 지표 조사 담당자
> 필요한 증거: 승인된 지표 정의와 실제 계산 구현
> 영향: 산식 확정과 계산 검증을 보류한다. 화면 구성 조사는 계속한다.
```

추정은 `가정:`으로 표시하고 근거·영향·해소 담당을 기록한다. 핵심 사실을 가정으로 채운 상태에서 최종 검증 완료를 선언하지 않는다.

## 6. 제목·본문·목록

- 파일당 H1 하나. H2/H3를 순서대로 사용하고 제목 단계를 건너뛰지 않는다.
- 제목·표·목록·코드 블록 앞뒤에 빈 줄을 둔다.
- 절 번호는 편집 순서를 따라 관리한다. 페이지 번호를 Markdown에 수동 기입하지 않는다.
- 버튼·메뉴는 실제 표시명을 쓴다. 코드 식별자·경로·컬럼·필드는 백틱으로 구분한다.
- 절차는 번호 목록, 조건·특징은 글머리표, 비교·필드 정의는 표로 쓴다.
- 줄 길이나 글자 수를 맞추려고 임의 줄바꿈·공백·빈 행을 반복하지 않는다.
- 시스템 화면, 브라우저 탭, 문서 페이지를 구분해 표현한다.

## 7. 표 규칙과 회사 스타일

표에는 의미 있는 헤더를 붙이고 모든 행의 열 수를 맞춘다. 셀 안의 `|`는 이스케이프한다. 긴 절차·JSON·SQL은 표 밖으로 옮긴다. 열이 많아 가독성이 떨어지면 기본 정보·제약·관계 표를 분리한다. 지원 상태는 `지원 / 미지원 / 해당 없음`, 데이터 상태는 실제 정의에 따라 `0 / 데이터 없음 / 미확정`을 구분한다.

회사 테마가 표 헤더 색·테두리·줄무늬·셀 여백·정렬·헤더 반복·페이지 분할을 결정한다. 문서에는 `<font>`, 인라인 CSS, 색상 코드로 회사 서식을 직접 삽입하지 않는다. 새 표 스타일이 필요하면 공통 테마 계약에 이름과 의미를 정의한 뒤 적용한다.

### 페이지 기능 현황 예시

| 페이지 | 조회 | Drill-down | CSV 내보내기 | Excel 내보내기 | 저장 |
| --- | --- | --- | --- | --- | --- |
| 설비 목록 | 지원 | 지원 | 지원 | 지원 | 해당 없음 |
| 설비 상세 | 지원 | 미지원 | 지원 | 미지원 | 해당 없음 |

가상 예시이며 실제 지원 여부로 대체하기 전까지 예시 표시를 유지한다.

## 8. 강조·코드·이미지·링크

- 의미 마커는 `> [!NOTE]`, `> [!WARNING]`, `> [!EXAMPLE]`으로 통일한다. 파란 배경·왼쪽 마커 등 외형은 테마가 정한다. 렌더러가 의미 스타일을 지원하지 않으면 텍스트 라벨을 보존하고 서식 미지원으로 기록한다.
- 코드 블록에 `json`, `http`, `sql`, `text` 등 언어를 지정한다. 예시와 실제 계약을 혼합하지 않는다.
- 캡처에는 화면명, 선택 조건과 필요한 촬영 시점을 읽을 수 있는 대체 텍스트·캡션으로 설명한다. 화면 ID·증거 ID·해시는 관리용 사이드카에만 기록한다. 개인정보·계정·민감 업무 데이터는 마스킹한다.
- 작성한 안내와 캡처의 선택 상태를 일치시킨다. 캡처가 없으면 가짜 스크린샷으로 대체하지 않는다.
- 문서 내 파일 참조는 배포 묶음 기준 상대 링크를 쓴다. 개인 PC 절대 경로와 비밀 URL을 최종 문서에 남기지 않는다.
- 공통 정의를 복사해 다른 값으로 바꾸지 않는다. “공통 기준을 따르며 기본 기간만 최근 7일로 변경”처럼 차이를 명시한다.

## 9. 유형별 최소 예시 계약

| 유형 | 예시에 반드시 포함할 요소 |
| --- | --- |
| 매뉴얼 | 사용자 행동, 화면 결과, 필요 시 오류 후 다음 행동 |
| 기능 | 정상·경계·실패, 기대 결과, 검증 조건 |
| API | 유효 요청, 성공 응답, 오류 응답, null/빈값 의미 |
| 지표 | 입력 기록, 계산 과정, 단위, 기대값, 결측·분모 0 사례 |
| 테이블 | 컬럼 정의와 일치하는 샘플 행, 키 관계, NULL 의미 |

영문 변수는 실제 DB 컬럼이라고 가정하지 않는다. 예를 들어 `AvailableTime`은 계산 변수이며 실제 컬럼 연결은 별도 표에 기록한다. 예시 수치는 계산 검증하고 JSON 등은 구문 검사한다. 구문 통과와 실제 API·DB 실행 검증은 따로 기록한다.

## 10. 검토와 최종 산출물

Markdown 점검은 메타데이터, 필수 절, 근거 ID, 링크, 표 구조, 예시 표시, pending을 확인한다. 내용 검토는 실제 출처와 주장·기대값의 일치를 확인한다. 출력 QA는 요청한 각 형식을 직접 렌더링해 제목 고립·표 잘림·헤더 반복·이미지 가독성·머릿글·바닥글·마지막 페이지를 확인한다.

편집 검토자는 모든 원본 파일의 제목·문장·표 셀·예시를 처음부터 끝까지 읽는다. 글자 누락, 오탈자, 띄어쓰기, 조사·어미, 문장부호, 영문 대소문자, 용어와 실제 화면 명칭, 수치·단위·시간대를 대조한다. 대표 문단이나 일부 페이지만 읽고 전수 검토로 기록하지 않는다. 파일별 검토 범위와 버전, 정확한 문제 원문·위치·수정 제안·이유를 별도 검토 보고서에 남긴다.

텍스트 추출 일치는 내용 보존 검사이며, 실제 읽기와 시각 검수를 대신하지 않는다. 출력 형식마다 모든 페이지·시트·절을 확인하고, 해당 렌더러가 없거나 선행 실패로 확인할 수 없으면 미검증으로 남긴다. 전체 회차의 실행과 독립 검토가 끝난 다음 수정하고, 수정 후 같은 전체 케이스와 추가 발견 케이스를 다시 실행한다.
